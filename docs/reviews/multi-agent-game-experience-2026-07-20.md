# 《谁是 AI》多用户并行体验问题与修复计划

体验日期：2026-07-20
体验基线：本地 Go 服务 `http://127.0.0.1:3014`
体验方式：3 个独立体验 agent，分别覆盖正常联机、测试模式和单人调试。本轮只记录问题，不修改实现。

## 一、覆盖范围

### 正常联机

- 1 个浏览器真人 + 2 个独立 Socket 真人 + 2 个 AI。
- 完成 3 轮任务胜利局。
- 覆盖创建房间、AI 补位、身份揭示、提名、聊天、公开立场、队伍投票、任务行动、真人超时托管、刷新恢复、结算与原班复玩。

### 测试模式

- 1 真人 + 5 AI。
- 覆盖任务成功和失败、快速推进、刷新恢复、390×844 窄屏、结算和复玩。

### 单人调试

- 1 真人 + 5 AI。
- 覆盖暂停/继续、暂停中跨阶段推进、指定下一任务成功/失败、刷新恢复、AI 状态、结算和复玩。

## 二、结论

本轮没有发现 P0 卡死或无法完成游戏的问题。核心状态机、多客户端同步、超时托管和胜负结算基本可靠。

当前最主要的风险是“社交证据生命周期”不完整：刷新会丢证据，复玩会把旧证据带入新局。对社交推理玩法来说，这两类错误比普通 UI 缺陷更严重，因为它们会直接改变玩家判断。

## 三、P1 问题与修复建议

### P1-01 刷新恢复后社交证据链不完整

影响模式：正常联机、测试模式、单人调试。

实际结果：

- 玩家身份、轮次、任务比分和当前阶段可以恢复。
- 投票历史、可疑事件、公开立场和部分聊天无法完整恢复。
- 正常模式聊天通常只剩当前轮；单人调试恢复瞬间历史区域为空。
- 暂停局刷新后，调试面板显示“已暂停”，顶部却显示 `⏱0:00`。

影响：掉线玩家无法依据前轮讨论、组队和投票继续推理；不同客户端拥有不同证据视图。

建议：

1. 将重连数据定义为完整的 `GameSnapshot`，统一包含角色、队长、提名、聊天、投票历史、立场、信号记录、可疑事件、任务状态、本人已执行动作、暂停状态和服务端时间。
2. 客户端只通过一个 `applyGameSnapshot` 恢复界面，避免多个事件各自补一部分状态。
3. 暂停恢复时优先渲染服务端 `debugPaused`，不从过期 `deadlineAt` 推导顶部状态。
4. 增加“刷新前客户端”和“恢复后客户端”快照等价测试。

验收标准：同一房间内，未刷新客户端与恢复客户端的所有推理证据一致。

### P1-02 原班复玩污染新局

影响模式：测试模式、单人调试；正常模式重新开局后也需要统一防护。

实际结果：

- 服务端比分、轮次和 AI 角色已经重置。
- 页面仍保留上一局聊天、投票历史、侦测记录、异常提示、讨论焦点和可疑事件。
- 新局消息继续追加在旧局消息后面。

影响：上一局证据会被误认为新局证据，直接污染推理。

建议：

1. 建立唯一的 `resetGameClientState`，同时清理 JS 内存状态和 DOM。
2. 清理范围至少包括：聊天、消息计数、投票历史、信号历史、提名历史、公开立场、讨论焦点、可疑事件、当前小队、任务动作、身份信息、计时器、Toast、调试状态和结算统计。
3. `roomReset`、返回首页、新房间和原班复玩都调用同一个 reset 函数。
4. 为“完成一局→原班复玩→新局第 1 轮”增加端到端回归。

验收标准：复玩只保留房间和玩家阵容；新局页面不存在任何上一局证据。

### P1-03 正常模式非任务成员缺少旁观界面

实际结果：非小队成员收到任务阶段和子阶段变化，但未收到 `missionSpectate`，主区域为空。

建议：

- 服务端任务开始事件必须给小队成员发送 `missionPuzzle`，给所有非小队成员发送 `missionSpectate`。
- 旁观界面展示任务名称、行动小队、当前子阶段、剩余时间和“等待秘密行动”状态，但不泄露个人行动。

验收标准：任意非小队真人在任务阶段都有明确可理解的等待界面。

### P1-04 正常模式无法公开信任或怀疑 AI

实际结果：正常模式公开立场下拉框只显示真人，AI 虽然会聊天、投票和公开站队，却不能成为真人的正式判断对象。

建议：

- 所有未淘汰玩家都应进入立场选择器，不按 `isAI` 过滤。
- 结算和 MVP 统计继续使用稳定玩家 ID，不因 AI 名称变化丢失记录。

验收标准：真人可公开信任或怀疑任意真人/AI 玩家。

### P1-05 身份阅读与首轮阶段并行

实际结果：身份揭示期间，其他真人队长可以提名，服务端讨论计时可能已经开始；测试模式复玩时甚至可能直接进入第一轮而没有可靠身份卡。

建议：

1. 服务端新增 `role_confirm` 或 `ready` 屏障。
2. 所有在线真人确认身份后再创建首轮提名截止时间。
3. 设置最长确认超时，超时玩家自动确认，避免房间永久阻塞。
4. 复玩必须重新发送并确认新身份。

验收标准：任何真人确认身份后都能获得完整首轮操作时间；其他玩家不能提前进入提名或讨论。

## 四、P2 问题与修复建议

### P2-01 自动托管缺少可追溯记录

- 秘密行动超时后，玩家难以确认自己是主动提交还是系统代管。
- 建议在下一阶段保留一次“系统已代你执行任务”的个人状态，并在结算统计中标记托管动作。

### P2-02 移动端核心操作距离过远

- 390×844 下无横向溢出，但顶部状态与提示浮层拥挤，聊天输入位于较深位置。
- 建议移动端将“聊天 + 当前操作”提升为首屏主区域，任务历史与玩家列表改为抽屉或折叠面板。

### P2-03 刷新后局后统计失真

- 中途刷新后游戏时长显示 `--`，聊天统计少于实际值。
- 建议游戏开始时间、结束时间和消息计数全部由服务端维护并随快照、结算包返回。

### P2-04 调试日志刷新后断档

- 建议按房间在客户端持久化本局调试日志，或明确标注“仅记录本页操作”。复玩时必须清空。

## 五、验证通过项

- 3 名真人到齐后房主可补 2 个 AI 并开局。
- 多客户端的队伍、阶段、票数和任务结果保持一致。
- 真人队伍投票超时按反对托管，并只向本人提示。
- 任务行动超时默认执行，不会卡死房间。
- 快速推进、暂停/继续、暂停中跨阶段推进正常。
- 强制下一任务成功/失败可以正确结算。
- AI 已能引用上一轮成功/失败、失败小队和重复入队关系。
- 刷新可以恢复稳定玩家 ID、身份、轮次和任务比分。
- 结算角色、胜负、任务记录和复玩入口可用。
- 游戏页面自身没有发现 JavaScript `error` 或 `warn`。

## 六、建议实施顺序

1. `resetGameClientState`，解决复玩证据污染。
2. `GameSnapshot + applyGameSnapshot`，解决刷新恢复证据缺失和统计失真。
3. 补齐正常模式 `missionSpectate`。
4. 允许立场选择 AI。
5. 服务端身份确认屏障。
6. 自动托管记录、移动端布局和调试日志范围说明。
