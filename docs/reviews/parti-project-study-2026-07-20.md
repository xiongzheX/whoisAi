# Parti 项目学习与《谁是 AI》迁移建议

学习日期：2026-07-20
上游仓库：[glink25/Parti](https://github.com/glink25/Parti)
学习版本：`2dc7c1e024c41b75cbe4b91e8e5e7866b6e1d9ab`
关联体验记录：[《谁是 AI》多用户并行体验问题与修复计划](./multi-agent-game-experience-2026-07-20.md)

## 一、结论

Parti 最值得当前项目学习的不是界面或具体规则，而是它对多人房间生命周期的约束：

1. 玩家只发送语义动作，权威端统一改变状态。
2. 可恢复的事实放进完整快照，一次性提示只作为事件发送。
3. 重连是原玩家回归，不是新玩家重新加入。
4. 新一局必须有新的轮次边界，客户端派生状态随之失效。
5. 私密信息与公开状态分开，但仍要为私密信息设计恢复策略。

这些原则能直接解决当前《谁是 AI》的刷新证据丢失、复玩证据污染、身份阅读被抢跑和操作反馈不确定等问题。不过不建议把项目整体改造成 Parti 的“房主浏览器权威”架构；《谁是 AI》已有 Go 服务端，继续让服务端保持权威更适合公开联机、AI 调度和隐藏身份保护。

## 二、Parti 是什么

Parti 是一个让用户创建、导入和运行多人互动房间的 Web 平台。一个房间主要由清单、页面和 Worker 逻辑组成；平台负责协议、传输、同步、重连、沙箱和回放。

它的适用范围偏朋友、家庭和轻社交房间，不以强对抗、反作弊和高风险公共竞技为目标。因此，它对《谁是 AI》的主要参考价值是“轻量社交房间运行时”，而不是完整的商业社交推理游戏方案。

核心结构可以概括为：

```text
玩家 UI --提交 action--> 权威端 Worker --修改 state--> 完整 snapshot --广播--> 所有 UI
                              |
                              +--私密 event--> 指定玩家
```

## 三、关键设计与可迁移价值

### 3.1 语义动作，而不是客户端直接改状态

Parti 客户端提交的是 `round:deal`、`round:eliminateSelf` 等动作。权限校验、规则判断、随机结果和状态修改全部在权威端完成。

迁移到《谁是 AI》：

- 客户端继续只提交 `proposeMission`、`teamVote`、`missionVote`、`submitStance` 等意图。
- 服务端统一返回动作结果及新状态，客户端不应根据“发送成功”自行推断“业务已接受”。
- 每个重要动作需要明确的 `actionId` 或等价标识，避免重试造成重复投票、重复发言或重复提交任务。

### 3.2 持续状态与一次性事件分离

Parti 的规则是：刷新后仍必须存在的内容属于 state；动画、音效、临时提示等属于 event。新玩家或重连玩家会先收到欢迎信息和当前完整快照，而不会依赖把历史事件重新播放一遍来拼装页面。

这与当前项目的问题直接对应：

| 当前内容 | 建议归属 | 原因 |
| --- | --- | --- |
| 房间、玩家、轮次、阶段、截止时间 | 公共快照 | 所有人恢复后必须一致 |
| 提名、理由、聊天、投票、公开立场、任务结果、可疑事件 | 公共证据快照 | 是后续推理依据，不是临时 UI |
| 本人身份、本人是否已投票、本人任务行动、侦测者私密信息 | 玩家私密快照 | 必须恢复，但不能广播给他人 |
| Toast、音效、阶段切换动画 | 一次性事件 | 丢失或不重放不影响规则 |
| 自动托管提示 | 私密快照中的结果 + 一次性提示 | 既要当下提醒，也要允许刷新后查证 |

当前 `ReconnectEvents` 通过多种事件重新拼页面，容易遗漏证据。更稳妥的方案是一次发送 `GameSnapshot`，由客户端唯一的 `applyGameSnapshot` 原子恢复。

### 3.3 稳定身份与显式重连

Parti 为客户端保存稳定 `clientId`，服务端维护 `clientId → playerId` 映射。断线后玩家先进入离线宽限期；在宽限期内返回会复用原身份并触发 `onReconnect`，不会再次触发 `onJoin`。

迁移到《谁是 AI》：

- 房间内身份应绑定稳定的重连令牌，而不是只依赖瞬时 Socket ID。
- 断线只改变在线状态，不应立刻删除玩家或其投票、聊天和身份。
- 重连处理与首次加入分开，避免重复欢迎、重复身份分配和重复首轮事件。
- 服务端向重连者同时发送最新公共快照和该玩家的私密快照。

### 3.4 快照版本与原子应用

Parti 的快照包含单调递增的版本号和状态哈希；客户端会忽略旧版本，权威端恢复后也延续原版本，避免时间倒流。

建议为当前项目的 `GameSnapshot` 增加：

- `gameId`：每次开新局都变化，用于隔离复玩数据。
- `version`：本局内单调递增，用于丢弃乱序状态。
- `serverNow`：统一倒计时基准。
- `phaseDeadline` 与 `debugPaused/debugRemainingMS`：由服务端决定计时展示。
- `publicState` 与 `privateState`：同一版本下原子应用。

客户端接收新快照时建议遵循：

```text
gameId 变化       -> 清空上一局所有派生状态，再应用新快照
同 gameId 版本更高 -> 原子替换权威状态，重新计算 UI
同 gameId 旧版本   -> 忽略
```

这比维护多个 `voteHistory`、`signalHistory`、`suspicionTimeline` 等全局数组并分别补事件更不容易产生脏状态。

### 3.5 `ready` 屏障适合身份确认

Parti 把玩家的连接与 `ready()` 分成两个状态，并提供独立 `onReady` 生命周期。当前项目可以借鉴这个思路实现首轮身份确认：

1. 服务端完成发身份后进入 `role_confirm`。
2. 真人点击“我已了解身份”后提交确认。
3. 全部在线真人确认，或确认超时后，服务端再创建首轮阶段和倒计时。
4. 重连与原班复玩都重新核对当前 `gameId` 下的确认状态。

这样能避免身份卡尚未读完，其他玩家已经提名或讨论的体验割裂。

### 3.6 回放记录适合作为社交证据诊断工具

Parti 的平台层会记录快照和事件，并用房间包哈希绑定回放版本。当前项目不必立刻做完整可播放回放，但可以先实现服务端的本局事件账本：

- 记录阶段切换、提名、聊天、公开立场、投票、任务结果、托管动作。
- 每条记录包含 `gameId`、`version`、`round`、`actorId`、服务端时间和动作来源。
- 调试模式读取同一账本，不再单独维护刷新即丢失的前端日志。
- 结算统计从服务端账本生成，解决刷新后时长和消息计数失真。

## 四、不应直接照搬的部分

### 4.1 不改成房主浏览器权威

Parti 适合朋友房和轻社交，但《谁是 AI》需要服务端安全持有角色、AI 决策、任务破坏结果和计时器。继续使用 Go 服务端权威，能减少房主退出、作弊和浏览器后台挂起带来的风险。

### 4.2 不把秘密恢复只寄托在内存事件上

短生命周期运行时中的秘密状态一旦随房主刷新丢失，长局游戏就无法可靠恢复。

《谁是 AI》一局更长，不能默认因房主刷新而作废。角色、本人行动和私密线索需要留在服务端权威状态，并通过按玩家裁剪的私密快照恢复；绝不能放入所有人可见的公共快照。

### 4.3 不以完整快照替代游戏边界

完整快照解决的是同一局内的一致性，不会自动解决复玩污染。必须同时引入 `gameId`，并规定上一局与下一局之间的清理边界。

### 4.4 不把动作发送成功当作业务成功

Parti 客户端 action Promise 只代表消息已发送。当前项目应提供业务确认或等待更高版本快照，按钮在得到权威结果前保持“提交中”，失败时恢复可操作状态并显示具体原因。

## 五、对上一轮修复顺序的调整

综合 Parti 的设计，建议按以下顺序实施：

1. 引入 `gameId` 和统一 `resetGameClientState`，先阻断复玩污染。
2. 定义 `GameSnapshot`、`PlayerPrivateSnapshot`、`version` 和 `serverNow`。
3. 用单一 `applyGameSnapshot` 替代重连时的多事件拼装。
4. 补齐正常对局中的 `missionSpectate`，明确所有无操作阶段的主视图。
5. 增加 `role_confirm`/`ready` 屏障，并建立不可被普通弹窗打断的交互优先级。
6. 将 AI 纳入正式信任/怀疑对象，保证社交证据覆盖所有参与者。
7. 增加动作确认、幂等标识和自动托管记录。
8. 以服务端事件账本统一支撑调试日志、结算统计和后续回放。
9. 最后再优化移动端信息层级和探索一台设备/围观入口。

## 六、建议验收场景

### 快照与重连

- 任意阶段刷新后，公共证据、本人身份、已完成动作和剩余倒计时与未刷新客户端一致。
- 重连不重复加入、不重复分配身份、不重复提交动作。
- 乱序到达的旧版本状态不会覆盖新状态。

### 复玩隔离

- 结算后原班复玩产生新的 `gameId`。
- 新局第 1 轮不存在上一局聊天、投票、立场、可疑事件、Toast 或调试日志。
- 延迟到达的上一局事件因 `gameId` 不符被忽略。

### 身份确认与弹窗优先级

- 未完成身份确认前不能开始首轮提名和倒计时。
- 填写提名理由、怀疑理由或聊天时，不出现普通邀请、组队或引导弹窗。
- 网络断开、房间关闭等高优先级系统状态仍能覆盖当前交互。

### 旁观与反馈

- 每个阶段、每种角色和是否在任务小队的组合都有明确主视图。
- 动作提交中、已接受、被拒绝、超时托管均有可追溯状态。
