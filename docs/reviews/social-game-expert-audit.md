# 谁是AI社交游戏专家审查

审查时间：2026-04-28

## 核心判断

当前项目的好方向是“阿瓦隆式组队投票 + AI 附身信息污染”。这个定位有传播点，但现状还没有形成稳定可玩的首局体验：Node 主后端无法启动，浏览器首局会因 Socket.IO client 缺失卡死，规则文案和真实流程不一致，任务阶段从“破坏/成功”变成“谜题投票”但玩家引导没有跟上。

专家结论：优先级不是继续加角色或加视觉特效，而是先修成“一局能顺畅开始、知道自己为什么做选择、每次状态变化都有明确下一步”的派对游戏闭环。

## P0 阻断问题

### 1. Node 主后端启动失败

证据：

`node /Users/xiongzhe/myIdea/谁是AI/server/server.js` 直接失败：

```text
Error: Cannot find module './topicBank'
Require stack:
- server/phaseHandlers.js
```

缺失模块：

- `server/topicBank.js`
- `server/possessionEngine.js`
- `server/puzzleBank.js`

引用位置：

- `server/phaseHandlers.js`
- `server/missionHandlers.js`

影响：

玩家无法进入当前 README 描述的完整 Node 版游戏。任何玩法、UI、节奏优化都无法被真实验证。

验收标准：

- `npm run server` 能正常监听端口。
- `npm run check` 不再因为缺模块失败。
- 测试/单人模式能从登录进入等待室，再进入角色揭示。

### 2. Go 后端首局浏览器阻断：`io is not defined`

证据：

访问 `http://127.0.0.1:3012/` 后点击开始游戏，控制台报错：

```text
ReferenceError: io is not defined
at joinGame (client/js/game.js:371)
```

HTML 依赖 `/socket.io/socket.io.js`：

- `client/index.html`

当前 Go 迁移服务没有正确提供 Socket.IO client 脚本，导致前端无法连接。

影响：

Go 后端虽然 `/socket.io/?EIO=4&transport=polling` 能握手，但用户无法通过页面开始游戏。

验收标准：

- 使用 `npm run go:server` 打开页面后，`window.io` 存在。
- 点击开始游戏不会触发 `io is not defined`。
- 测试模式能自动补 AI 并进入游戏。

## P1 核心体验问题

### 3. 游戏规则心智不一致：README/帮助/实际执行阶段互相打架

现有玩家预期：

- README 和帮助面板说“小队成员选择成功或破坏”。
- 角色描述说渗透者在执行任务时投“破坏”。

实际代码：

- `server/missionHandlers.js` 已改为谜题 A/B/C 投票。
- 小队成员先看题、讨论、再选答案。
- 错误答案等价于任务失败。

影响：

玩家不知道自己是在玩“阵营破坏游戏”还是“协作答题游戏”。渗透者的破坏行为也从“点破坏”变成“故意选错答案”，但 UI 和角色说明没有把这件事讲清楚。

建议方向：

统一成“系统维护谜题”表达：

- 好人：协作找正确修复方案。
- 渗透者：伪装推理，诱导或选择错误方案。
- AI 附身：可能改写讨论发言，也可能让小队成员看到被扭曲的信息。

验收标准：

- README、登录页快速提示、帮助面板、角色说明、任务按钮文案一致。
- 不再出现“投成功/破坏”和“选 A/B/C 谜题”混用。

### 4. 首屏营销噪音破坏信任

证据：

登录页显示：

- “超过1000局已开”
- “4.9分好评”

这些没有数据来源，且项目处于原型阶段。

影响：

社交游戏的信任建立来自“规则清楚、朋友能快速进房”，不是虚构背书。假社交证明会降低玩家对产品完成度的信任。

验收标准：

- 移除虚构局数/评分。
- 替换为真实有用信息，例如“测试模式会自动补 AI”、“复制房间号给朋友即可同房”。

### 5. 流程推进缺少玩家可理解的下一步

问题表现：

- 提名阶段、讨论阶段、投票阶段、执行阶段都依赖 toast 短提示。
- Toast 消失后，页面固定区域没有清楚告诉玩家“现在谁要行动、我是否能操作、下一阶段何时开始”。
- 等待室玩家计数初始显示 `0 / 6`，即使用户已点击开始也没有稳定反馈，遇到错误只出现通用“游戏出现错误，请刷新页面重试”。

建议方向：

在主游戏区增加稳定的阶段目标文本：

- 提名：`队长：X，需选择 N 名小队成员`
- 讨论：`每人最多 6 条，重点判断小队是否可信`
- 投票：`是否批准该小队执行维护任务`
- 执行：`小队成员讨论并选择修复方案`
- 揭晓：`查看小队答案与任务结果`

验收标准：

- 每个 phase 都有固定区域显示“当前目标”和“你的动作”。
- 非行动玩家看到等待对象，而不是只看到不可用按钮。

### 6. 任务阶段客户端事件不完整，揭晓体验会断层

证据：

服务端发送：

- `missionPuzzle`
- `missionSpectate`
- `missionSubPhase`
- `puzzleChatBroadcast`
- `missionReveal`

客户端已有 UI 函数：

- `showPuzzle`
- `enablePuzzleVote`
- `enablePuzzleChat`
- `showSpectate`
- `showReveal`

但主事件注册区没有完整呈现这些事件的监听闭环，普通 `missionResult` 只显示简略 toast。结果是任务阶段作为本游戏特色，却可能只以零散提示呈现。

验收标准：

- 客户端显式监听并处理 `missionPuzzle`、`missionSpectate`、`missionSubPhase`、`puzzleChatBroadcast`、`missionReveal`。
- 小队成员在讨论子阶段能看到题目但不能投票，投票子阶段可点选项。
- 非小队成员看到旁观提示。
- 揭晓阶段显示正确答案、每人答案、最后一句理由和是否发生附身。

### 7. 角色和人数配置扩展了，但 UI/文案只解释 3 个角色

代码已有：

- 工程师
- 渗透者
- 信号员
- 观察者
- 保护者
- 干扰者

但帮助面板只解释前三个角色，README 也偏 6 人旧规则。角色图标映射也只覆盖前三个。

影响：

玩家抽到观察者/保护者等角色时，会缺少预期和操作入口。更严重的是这些角色能力在当前流程中不一定真实可用。

建议方向：

短期收敛角色池：只保留已经有完整玩法闭环的角色。扩展角色先不进正式分配。

验收标准：

- 角色分配只发放有真实能力或清楚定位的角色。
- 帮助面板覆盖所有可能出现的角色。

## P2 画面与可用性问题

### 8. 标题在可访问树重复三次

浏览器快照中标题为：

```text
heading "谁是AI 谁是AI 谁是AI"
```

原因可能是 glitch 标题的 `data-text`/伪元素处理影响可访问名称。

影响：

屏幕阅读器体验差，也暴露出视觉特效压过基础语义。

验收标准：

- H1 的可访问名称只读作一次“谁是AI”。
- glitch 视觉层对辅助技术隐藏。

### 9. 表情符号过多，信息层级不稳

登录、等待、帮助、按钮、toast 中大量 emoji 同时承担图标、情绪、状态含义。派对感是优点，但现在会让关键状态淹没在装饰里。

建议方向：

- 保留角色图标和任务结果图标。
- 关键按钮减少装饰性 emoji。
- 错误/成功/警告状态统一图标语义。

验收标准：

- 主要操作按钮能在无 emoji 情况下读懂。
- 状态图标含义一致。

### 10. 调试能力和正式体验混在一起

页面中包含完整 debug panel、跳阶段、AI 状态等结构。虽然默认 hidden，但测试/单人模式容易变成面向开发者而不是面向玩家。

建议方向：

- “测试模式”服务产品验证；“单人调试”服务开发者。
- 默认登录页推荐“测试模式”的文案要说明它是体验局，不要暴露开发调试味。
- Debug panel 只在 URL 参数或显式开发开关下出现。

验收标准：

- 普通玩家不会看到“调试面板/跳阶段/AI状态”等开发术语。
- 开发者仍能通过 `?debug=1` 或单人调试打开。

## 推荐执行顺序

1. 修启动阻断：补齐 Node 缺失模块，或修 Go 服务提供 Socket.IO client 脚本，至少保证一个后端可完整进入游戏。
2. 修任务阶段事件闭环：让谜题讨论/投票/揭晓真实可见。
3. 统一规则文案：把“成功/破坏”收敛为“维护谜题正确/错误选择”或反过来。
4. 优化首屏与阶段引导：移除虚构背书，增加固定目标文本。
5. 收敛角色池和帮助文案。
6. 再处理视觉语义、emoji、debug 暴露等 P2 问题。

## 执行工程师本轮目标

本轮不要试图重做全部游戏。优先完成以下可验证目标：

- 至少一个后端能从首页进入测试局，不出现控制台致命错误。
- Node 后端缺失模块问题被修复，`npm run check` 能过。
- 前端任务阶段事件处理补齐，A/B/C 任务闭环可见。
- 登录页移除虚构社交证明。
- 帮助/提示文案和谜题任务制一致。

完成后，执行工程师需要回报：

- 修改了哪些文件。
- 哪些 P0/P1 已解决。
- 运行了哪些验证命令。
- 哪些专家问题仍未解决及原因。
